# Six-edge build admission is still closed

The coordinate, native helper, tiny builders, complete four-edge audit and binary
restart pilots now have separate saved results. This brief reconciles their
limits before any full six-edge allocation or costly run. It grants no authority.

`bench/edge-build-geometry.mjs` derives cardinality independently as
`12! / (12-k)! * 2^k` and checks the actual declared constants. It reads the
emitted native array allocation and storage functions rather than treating every
runtime Term as one U32 cell. The current compiler emits unboxed buffers for
these U32 arrays. Their payload storage is four bytes per capacity cell.
That is not resident memory or total generation scratch.

The six-edge geometry has 42,577,920 logical states and requires a power-of-two
capacity of 67,108,864 cells. The unboxed array payload alone is 268,435,456 bytes.
A raw U32LE checkpoint has 170,311,680 bytes in 650 existing IO chunks. Two raw
input/output files need 340,623,360 bytes. Complete eighteen-move graph coverage
contains 766,402,560 directed edges per pattern, or 1,532,805,120 for both.
These are checked size calculations, not allocations or executed audits.

The four-edge restart evidence covers 760,320-byte payloads and a 262,144-cell
array. Its native boundary deliberately rejects larger geometry. Neither the
native adapter nor the manifest admits six-edge checkpoints. Its 5.79 s CPU
total includes several commands, seeds, repeats and failures. It cannot supply
a full-generation ETA, large-profile RSS, retention budget or independent audit
cost. The earlier six-edge helper's five 100,000-call samples are also not a
generator or audit benchmark. Reuse them as helper evidence, not an ETA.

Eight actual source or record corruptions must make the size check fail. They
cover wrong cardinality, boxed or shared arrays, changed storage layout, word
size, chunk size, checkpoint capacity and pilot byte count. The test allocates
no six-edge array, and the existing audited pilot is not rebuilt.

The remaining U03 gates are explicit.

- Human approval of the exact NP04 and NP05 statements in
  `docs/architecture/NEXT-PROOF-STATEMENTS.md`, followed by their proofs and the
  concrete data and projection bridges.
- A separately approved large-build and full-audit budget. Proposed work must
  keep the resource policy and thirty-minute batch ceiling, preserve resumable
  identity, and account for full checkpoint retention and audit scratch.
- A six-edge-specific native admission and checkpoint boundary before any such
  build. Four-edge runtime checks cannot be relabeled as that boundary.
- Full independent data audits and information/cost evaluation before pruning
  or a default change. Four-edge zero marginal cuts do not reject six edges.

The read-only `u03-build-admission-v1` batch is estimated under one minute,
capped at two minutes, on CPU2 under 256 MiB. It verifies source and archived
identities, the current runtime layout, size arithmetic and eight corruptions.
No distance generation, new proof, performance run, holdout or publication.

## Result

The [canonical archive](u03-build-admission-v1/index.json) verifies 3,013 source
seals and two receipts, worker gone and no resource stop. All six independent
cardinalities, current emitted storage checks and eight actual corruption
controls pass. No large buffer is allocated. The current native checkpoint
remains four-edge-only. Full build admission remains closed.

Static payload arithmetic is now checked, but actual full-capacity allocation
and IO costs are not. A bounded synthetic buffer test can measure those without
creating distances or running BFS. Its words must be independently verified,
deliberately invalid as distance data and kept separate from every solver cache.
Even that test cannot supply full-generation or independent audit time.
