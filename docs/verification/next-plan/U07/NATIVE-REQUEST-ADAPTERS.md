## Initialization and request ownership

Cold-process and warm-request clocks must remain distinct. A process restart
after every exact-search timeout would repeatedly reload tables and would not
establish a retained warm-request contract. The selected comparison-only native
services load their data once in a single-threaded parent. Each request runs in
one forked process group that inherits the loaded data. The parent enforces a
monotonic deadline, kills a timed-out group and reaps it with `wait4` before
serving another request. A child gets a parent-death signal. A subreaper captures
orphan descendants. A completed child that leaves a live group produces an
error and forced descendant cleanup, not a successful result.

The eight real-process controls cover a hung child, normal answer, failed child,
empty solved answer, partial output followed by a hang, an orphan retaining its
pipe, a silent orphan after direct-child completion and subsequent recovery.
All pass in the focused local fixture. Timeout output remains raw evidence but
cannot become an accepted candidate. Eleven malformed protocol-record controls
pass. These checks do not claim that any external solver is faster.

`READY` follows actual parent initialization. It reports native-parent cumulative
CPU through readiness, excluding the sandbox launcher and JS driver. Each
complete request frame reports controller elapsed time, waited request-child
user/system CPU, maximum single-child RSS, exit/signal status, reaped-process
count and fault flags. Those counters are not aggregate physical memory or the
whole parent lifetime. A later parent-clock adapter still has to timestamp packet
arrival, apply deadline eligibility and retain late/error/no-answer outcomes.
No measured fixture can be relabelled as a final comparison record.
